01

Premise

Difficulty changes while an agent works.

A software-engineering agent moves through exploration, planning, editing, testing, diagnosis, recovery, and verification. These phases do not demand the same level of model capability.

Initial prompts are incomplete routing signals: the important evidence often appears only after the agent has inspected the repository or interacted with tools. Yet reconsidering the model at every call creates unnecessary switching, cache loss, and inconsistent plans.

Problem

A coupled decision with a delayed outcome.

Decision A

When should the system route?

Decide whether new trajectory evidence makes reconsideration valuable enough to justify routing and handoff overhead.

open_checkpoint(s) ∈ { no, yes }
Decision B

What execution team should continue?

Continue centrally, switch the coordinator, or spawn a sub-agent; then assign every active role a model, context tier, and reasoning budget.

action(s) = graph × model × context × budget
Prompt-only One decision

Efficient, but blind to evidence discovered during execution.

Per-call Every decision

Adaptive, but granular, myopic, and prone to unnecessary switching.

Checkpoint Selective decisions

Route only at information-bearing events and optimize the remaining episode.

Research statement

How can a long-horizon system determine when to revise its execution graph and which model–context configuration should power each continuing or newly spawned agent, given shared state, local histories, progress, failures, dependencies, and budget?

The objective is to preserve frontier-model task completion while reducing total episode cost and latency—including coordination and context-transfer overhead—while avoiding routing or delegation decisions that add no value.

03

Prior art

The field is active. The opportunity is specific.

This project does not claim to invent multi-turn routing. It builds on query routers, cascades, partial-trajectory escalation, and per-turn agent routers.

Query

Single-turn adaptive routing

PILOT frames model selection as a budget-aware contextual bandit that learns from feedback on the selected model.

No evolving environment state
Prefix

Partial-trajectory escalation

SWE-Router uses early software-agent exploration to decide whether a cheap model should continue or a stronger model should restart.

Primarily one escalation point
Turn

History-aware multi-turn routing

MTRouter selects a model at each turn from the interaction history and candidate-model representation.

Decision timing is fixed
Step

Per-step agent routing

TwinRouterBench evaluates routing on every agent call; AgentRouter describes dependency-aware tier selection across workflow steps.

Often local labels or every-call decisions
Team

Dynamic and heterogeneous agent teams

DyLAN selects agent teams, while Heterogeneous Swarms jointly optimizes model roles and a collaboration DAG.

Usually task-level or offline graph optimization
Context

Short/long context routing

FleetOpt routes requests across serving pools with different effective context windows; Lost in the Middle shows that a longer context is not automatically better used.

Infrastructure or recall, not agent assignment
Sequence

Sequential routing and cascading

Router-R1, RLCascadeRouter, AutoMix, and TREACLE establish RL, POMDP, and constrained cascade foundations.

Usually answers, not persistent tool environments
Defensible positioning

The research gap is not “routing during long-horizon tasks” or “using multiple agents.” Both already exist. The narrower claim is joint, event-triggered control of when the execution graph changes and which model–context pair powers each agent, trained and judged by terminal episode outcomes with explicit handoff cost.

04

The exact gap

Existing systems optimize slices. The episode couples them.

Model routing, context-pool routing, and multi-agent orchestration are established research areas. What remains underexplored is a single controller that makes these choices together as new evidence arrives inside a persistent tool-using episode.

Novel hypothesis

A sparse controller that assigns (model, context tier, reasoning budget) when it changes the agent graph will produce a better episode-level success–cost–latency frontier than prompt-only, per-step, or static role–model allocation.

Clear falsifier

If a fixed role–model table or simple rule-based escalation policy matches the learned controller after all routing, context transfer, and coordination costs are counted, the joint router is not operationally justified.

05

Research opportunity

From next-response quality to remaining-episode value.

01

Checkpoint discovery

Compare fixed-turn, event-triggered, phase-aware, and learned decisions.

02

Model × context pool

Treat capability and usable context as separate axes; choose the smallest sufficient context tier, not automatically the longest.

03

Sub-agent assignment

At spawn time, match explorer, coder, reviewer, or verifier roles to a model, context packet, and budget.

04

Global episode value

Predict terminal success and remaining resources across interacting agents, not isolated response quality.

05

Counterfactual branches

Restore identical checkpoints and vary graph, model, or context assignment to estimate marginal value.

06

Coordination-aware control

Measure context transfer, parallelism, merge delay, duplicate work, inconsistency, cache loss, and replanning.

Important distinction: for hosted APIs, the maximum context window is mainly a feasibility constraint while actual input tokens drive price. For self-hosted fleets, configured context capacity also changes KV-cache concurrency and energy efficiency. The study should therefore log both model capability and context allocation instead of treating “long-context model” as a single quality tier.

06

Formalization

A constrained semi-Markov decision process.

Episode objective

maxπ Eπ[Y]
subject to Eπ[C] ≤ BC Eπ[L] ≤ BL

Y is terminal success, C is total cost across all agents, L is wall-clock latency, and π is the controller. Variable time between events and parallel sub-agent execution make this a constrained semi-Markov control problem.

Joint action at checkpoint k

ak = (gk, {mi, wi, bi}, hk)
gkcontinue, spawn, stop, retry, or merge agents mimodel assigned to active agent i wicontext tier and selected context packet bireasoning, token, and tool-call budget hkhandoff / aggregation policy

State: sk combines the shared environment snapshot, task graph, global budget, active-agent states, local histories, context occupancy, progress and failure signals, and uncertainty. The action is joint because changing one worker changes the information and budget available to the rest of the team.

Phase 1 · feasible now

Two-model escalation

One cheap model, one strong model, and three interpretable checkpoints: after initial exploration, first meaningful test failure, and repeated lack of progress.

  • Actions: continue cheap or escalate permanently
  • Learning: calibrated classification + cost regression
  • No reinforcement learning required
Phase 2 · core study

Context-aware sub-agents

Add a coordinator with at most two spawnable workers. At spawn, choose the role, model tier, compact or expanded context packet, and execution budget.

  • Independent capability and context-size ablations
  • Events: phase boundary, context pressure, failure, and merge
  • Measure useful work versus duplicate coordination work
Phase 3 · learn

Counterfactual joint policy

Branch restorable checkpoints across graph, model, and context assignments; learn calibrated outcome and resource predictors only after simple baselines show headroom.

  • Terminal success as the primary target
  • Repository- and task-family splits
  • Offline constrained RL remains optional

Feasibility

The router is cheap. The evidence is expensive.

Practical

A focused first study

  • Two model tiers and two context tiers
  • One coordinator and at most two workers
  • Four event-triggered decision types
  • Supervised value prediction
  • Small millisecond-scale router
Not practical initially

A complete policy tree

  • Unbounded agent spawning
  • All model × context × graph combinations
  • Unrestricted switching, restarts, and merges
  • Online reinforcement learning
  • Claims without live episode evaluation
Illustrative collection cost
1,000 × 3 × 3 × $0.50
≈ $4,500

Tasks × checkpoints × actions × average continuation cost—before infrastructure and final evaluation.

Most honest expectation

A bounded coordinator–worker study is practical; a fully general graph controller is not. The strongest competitor may be a static table: strong model for planning/review, cheap short-context model for scoped workers, and escalation after failed tests. The learned router must beat that policy materially after coordination overhead—not just statistically.

Expected contributions

A useful result, whether the router wins or not.

01

A formal definition of selective graph-and-resource routing for long-horizon agent systems.

02

A taxonomy and detector for progress-, phase-, failure-, context-, and budget-sensitive checkpoints.

03

A counterfactual dataset varying sub-agent graph, model tier, and context allocation from identical states.

04

A bounded supervised controller and a constrained multi-agent semi-Markov formulation.

05

An episode evaluation protocol covering success, total cost, latency, context waste, coordination, and regret.

06

Evidence showing when learned joint routing is—or is not—better than static assignments and simple rules.
