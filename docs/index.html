01

Premise

Difficulty changes while an agent works.

A software-engineering agent moves through exploration, planning, editing, testing, diagnosis, recovery, and verification. These phases may demand different model capabilities and context.

Initial prompts are incomplete routing signals: important evidence often appears only after repository inspection, tool execution, or test feedback. The opportunity is to allocate resources as that evidence arrives, rather than treating the opening request as a complete description of the episode.

Routing does not have to mean escalating after failure. It can also mean changing a context packet, moving to a cheaper model for mechanical work, reducing effort during verification, or deliberately staying with the current plan. Whether these choices help must be measured at the episode level, including their overhead.

Decision B · Allocation

What configuration should continue?

Keep the current configuration or give the single agent a different model, context packet, or reasoning budget for the rest of the session. Introduce these choices in separate experimental phases.

action = model × context × budget

CheckpointWhen and how should the plan change?

Use information-bearing events to reconsider the allocation and judge its remaining-episode value.

Research statement

How can a single-agent long-horizon session determine when to revise its allocation and which model–context configuration should power the rest of the session, given its history, workspace state, progress, failures, and remaining budget?

The objective is to preserve frontier-model task completion while reducing total episode cost and latency—including handoff, cache, and context-transfer overhead—and avoiding routing decisions that add no value. Scope: one agent loop with one active model at a time. Sub-agents and multi-agent graphs are out of scope. The phases on the method page bound each experiment without reducing the agenda to failure recovery alone.
