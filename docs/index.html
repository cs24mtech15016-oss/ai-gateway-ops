01

Premise

Difficulty changes while an agent works.

A software-engineering agent moves through exploration, planning, editing, testing, diagnosis, recovery, and verification. These phases do not demand the same level of model capability.

Initial prompts are incomplete routing signals: the important evidence often appears only after the agent has inspected the repository or interacted with tools. Yet reconsidering the model at every call creates unnecessary switching, cache loss, and inconsistent plans.

02

Problem

Two decisions, one delayed outcome.

Decision A

When should the system route?

Decide whether new trajectory evidence makes reconsideration valuable enough to justify routing and handoff overhead.

open_checkpoint(s) ∈ { no, yes }
Decision B

Which model should take over?

Select the continuation whose expected terminal success is worth its remaining cost, latency, and switching risk.

action(s) ∈ { continue, escalate, switch, replan }
Prompt-only One decision

Efficient, but blind to evidence discovered during execution.

Per-call Every decision

Adaptive, but granular, myopic, and prone to unnecessary switching.

Checkpoint Selective decisions

Route only at information-bearing events and optimize the remaining episode.

Research statement

How can a long-horizon agent determine when model selection should be reconsidered and which model should execute the next phase, given its execution history, environment state, observed progress, failures, and remaining resources?

The objective is to preserve frontier-model task completion while reducing total episode cost and latency—and while avoiding routing decisions that add no value.

03

Prior art

The field is active. The opportunity is specific.

This project does not claim to invent multi-turn routing. It builds on query routers, cascades, partial-trajectory escalation, and per-turn agent routers.

Query

Single-turn adaptive routing

PILOT frames model selection as a budget-aware contextual bandit that learns from feedback on the selected model.

No evolving environment state
Prefix

Partial-trajectory escalation

SWE-Router uses early software-agent exploration to decide whether a cheap model should continue or a stronger model should restart.

Primarily one escalation point
Turn

History-aware multi-turn routing

MTRouter selects a model at each turn from the interaction history and candidate-model representation.

Decision timing is fixed
Step

Per-step agent routing

TwinRouterBench evaluates routing on every agent call; AgentRouter describes dependency-aware tier selection across workflow steps.

Often local labels or every-call decisions
Sequence

Sequential routing and cascading

Router-R1, RLCascadeRouter, AutoMix, and TREACLE establish RL, POMDP, and constrained cascade foundations.

Usually answers, not persistent tool environments
Defensible positioning

The research gap is not “routing during long-horizon tasks.” It is the joint study of selective checkpoint timing, episode-level action value, counterfactual continuation from the same environment state, and handoff cost.

Formalization

A constrained semi-Markov decision process.

Primary objective

maxπ Eπ[Y]
subject to Eπ[C] ≤ BC Eπ[L] ≤ BL

Y is terminal success, C is total episode cost, L is total latency, and π is the routing policy. The interval between checkpoints varies, which makes the natural formulation semi-Markov.

Practical action score

QY(s,a)eventual success − λCQC(s,a)remaining cost − λLQL(s,a)remaining latency − λSQS(s,a)handoff penalty

Phase 1 · feasible now

Two-model escalation

One cheap model, one strong model, and three interpretable checkpoints: after initial exploration, first meaningful test failure, and repeated lack of progress.

  • Actions: continue cheap or escalate permanently
  • Learning: calibrated classification + cost regression
  • No reinforcement learning required
Phase 2 · evidence

Counterfactual dataset

Generate alternative continuations from restorable checkpoints and quantify the marginal value of escalation under identical starting conditions.

  • Terminal success as the primary target
  • Cost, latency, tool calls, and recovery as secondary targets
  • Repository- and task-family splits
Phase 3 · extension

Selective sequential policy

Add learned checkpoint timing, multiple model tiers, de-escalation, and alternative handoffs only after the simple system demonstrates value.

  • Explicit switching penalties
  • Offline constrained RL as an optional extension
  • Safe shadow evaluation before live control

Practical

  • Three event checkpoints

  • Supervised value prediction
  • Small millisecond-scale router
Not practical initially

A complete policy tree

  • Branching every agent turn
  • All models at every checkpoint
  • Unrestricted switching and restart
  • Online reinforcement learning
  • Claims without live episode evaluation

Most honest expectation

A calibrated two-model escalation router is likely practical. A multi-model CMDP may be academically interesting but unnecessary. The strongest competitor may be a simple rule: escalate after failed tests, repetition, or stalled progress. The learned router must beat that rule materially—not just statistically—to justify operational complexity.
