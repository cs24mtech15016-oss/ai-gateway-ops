Method and phases

Keep the research vision. Bound each experiment.

The phases separate timing and model/context allocation before testing their interaction, all within one agent session. They scope implementation and evidence—not the overarching research statement.

Phase 1 · Model control

Checkpoint evidence + timing

One agent, two models, fixed tools and budgets. First measure five continuations from a sampled checkpoint; then compare request-level, fixed-prefix, per-call and adaptive checkpoint timing using one matched value model.

Evidence: continuation value, recovery/no-intervention strata, timing overhead, and terminal success–cost curves.

Phase 2 · Context allocation

Model × context pool

A bounded two/three-model pool with different context capacities and two predefined full/compact packet policies. Keep reasoning settings fixed; compare fixed, independently tuned, and joint model/context assignments.

Evidence: context sufficiency, actual token/cache use, and whether context choice changes the preferred model.

Phase 3 · Integrated control

Test the coupled decisions

Combine validated timing and model/context choices with repeated, reversible revisions inside one session, respecting tool-loop and provider-state locks. Compare a learned controller with composed component policies. Add a small reasoning-budget menu only in a separate ablation if justified.

Evidence: interaction gains beyond components, switch frequency, reliability under session caps, and net deployment benefit.

First executable study: Phase 1a, not the entire proposal

One software agent, one Cheap/Strong pair, an immutable scaffold, and at most one intervention. Sample checkpoints across normal progress, planning/testing transitions, and stalled states. The five branches below make outcome collection tractable; model labels describe measured capability/cost in this setting, not universal rankings.

D · Trajectory drop

Strong + workspace only

Keep the edited workspace but give Strong only the task and a short “continue from the current files” note. The Handoff Tax found this the best escalation interface, so it is a branch, not an afterthought.

E · Clean restart

Strong + initial task

Restore the original sandbox, not the edited checkpoint. Give the original task only. Prefix spend and elapsed time remain sunk; restart receives the residual budget, not a fresh episode.

What a snapshot must preserve

Base commit and workspace changes; container/dependency state; working directory and relevant shell/tool state; tool outputs and agent messages; random/configuration metadata; elapsed time and remaining spend/turn/tool limits. Snapshot only at quiescent tool boundaries. Test replay equivalence before trusting comparisons.

If a process or external service cannot be cloned consistently, restrict or document it. Do not silently call a message transcript a restorable environment.

Sampling without hindsight leakage

Include early, middle, and late checkpoints; stalled/error states; and normal low-risk/successful controls. Sample using visible prefix evidence. If final outcomes stratify analysis or sampling, keep them out of model inputs and report sampling weights and the resulting coverage.

All sibling checkpoints/branches stay in their task’s split. Group related issues and near-duplicates; hold out repositories where possible. Branch labels come from hidden terminal tests unavailable to the online router.

Comparability and uncertainty

Fix system prompts, tools, model versions, token limits, and stopping rules. Use a common residual spend/deadline and documented residual turn/tool caps. Do not force equal completion lengths; extra recovery steps are charged. Reserve worst-case call cost before dispatch and enforce caps.

Repeat stochastic continuations with recorded seeds where supported. Store each trial, not just the best outcome; use uncertainty intervals and test calibration. Differences identify effects in this controlled snapshot population—not general causal effects on all tasks.

Learn the simplest useful model

Start with tabular diagnostics plus a frozen history embedding, then logistic/gradient-boosted outcome and resource predictors. Fit per-action success likelihoods and cost/time regressions; select feasible actions using calibrated utility. Compare task-only and risk/progress proxies with equal capacity and training volume.

Feature extraction, gate inference, and serialization are deployment costs. No prefill activation access, new foundation-model training, or multi-agent orchestration is required.

08

System design

Three planes, one decision interface.

CheckpointRouter has three parts. The online plane runs one agent episode; every model call passes through the LiteLLM gateway, and the gateway makes every stay/switch decision. The offline plane branches saved checkpoints to produce training labels. The evaluation plane runs every policy on held-out tasks. CPR and every baseline sit behind the same decide() call, so comparisons are matched by construction.

Who owns what

Each job has exactly one owner.

The split follows what each piece can see. The gateway sees every message, every token bill and every open tool call, so it owns the decision. The harness owns only the sandbox. The decision engine is a pure function of features, so it can be swapped for any baseline.

New · gateway

CPR gateway plugin

LiteLLM pre- and post-call hooks; the decision point.

  • Maps model: "cpr" + a session header to the session's state.
  • Blocks a switch while a tool call is unanswered or the provider holds state (B1).
  • Detects triggers in tool output and calls decide() in-process.
  • Applies the packet: rewrites messages for COMPACT or DROP and keeps them on later calls.
  • Logs four token buckets and $ per call (B2, B4); reserves worst-case cost and rejects calls over the cap.
Runs on the LiteLLM, Redis and Postgres already in this repo.
New · harness

Harness adapter

A thin wrapper; the agent loop is unchanged.

  • Opens a session and sends the session header on every call.
  • Optional evidence header: diff size and files touched.
  • Serves two callbacks: restart the sandbox, and take a snapshot (label collection only).
In harness mode (option B below) this becomes the checkpoint hook that calls decide() itself.
New · offline

Snapshot service

Makes a checkpoint restorable.

  • Saves docker commit image, git diff, cwd and env, message log, rt, config and seed.
  • Replay check: restore, re-run the last tool calls, compare outputs and diff hash.
  • Snapshots that fail are excluded, not patched. Live processes are not captured.
New · offline

Branch runner + evaluator

Turns one snapshot into labelled outcomes.

  • One job = snapshot × action × seed, in a fresh container with the residual budget.
  • Hidden tests run only after the branch ends and give Y.
  • Parallel workers, limited by Docker memory and provider rate limits.
New · decision

Decision engine

Stateless scorer loaded inside the gateway plugin; trained offline and frozen.

  • Triggers: a test or build result; the same error 3× in 6 calls; first edit after exploring; a plan written; every k calls.
  • Features: test status, error repeats, edits, steps, context fill, cache warmth, lock, active model, steps since switch, rt, plus a frozen history embedding.
  • Menu F: allowed models × packets that fit the window and the remaining budget.
  • Q̂a = p̂a − λĈa − ηL̂a; revise if the best Δ̂ exceeds τ.
Reused

Existing stack

Already in this repository.

  • LiteLLM proxy, Postgres and Redis (docker-compose.yml).
  • Ollama for pipeline development on a laptop.
  • Harbor / Terminal-Bench runner.
  • LLMRouterBench Avengers-Pro baseline.
None of these train or evaluate the checkpoint controller on their own.

Harness contract

What the harness still does.

With decisions in the gateway, the agent itself needs no changes. Any OpenAI-compatible agent (Harbor's terminus-2, mini-swe-agent) works by pointing at the gateway. The harness only handles what lives in the sandbox.

Two things the gateway must handle carefully. (1) Packet persistence: after a COMPACT or DROP at call j, the harness keeps sending its full history, so the gateway swaps messages 0…j for the stored packet on every later call. It keys this on a hash of that prefix; if the agent trims its own history and the hash no longer matches, the gateway holds rather than guessing. (2) Latency on the request path: scoring is fast, but COMPACT adds a summary call before the model call. It is measured and counted in L.

Interface

One call for every policy.

The gateway calls this function. CPR, the fixed-prefix rule, the per-call router, SAAR and every other baseline implement it, so swapping a policy is a config change in the gateway. They see the same state and choose from the same menu, so differences come from the policy, not from the plumbing.

decide(state) → HOLD | Allocation(model, packet, budget)

state  = CheckpointState(
           features   x_t,        # φ(H_t, r_t): visible evidence only, never hidden tests
           menu       F,          # feasible (model, packet) pairs; always contains HOLD
           active     (m, κ),     # current model and packet
           remaining  r_t)        # spend, deadline, turn and tool caps
packet ∈ {FULL, COMPACT, DROP, RESTART}       budget fixed in v1

Build order and gates

The system is built in seven milestones (M0–M6), each with a go/no-go gate. Instrumentation and snapshots come before any learning. See Feasibility and gates.

10

Core opportunity: model × context pools

Match resources to the session as it evolves.

Context allocation for the single agent is the central opportunity, scoped in Phases 2–3. Routed handoffs and session-aware routers are grounding and comparators—not capabilities to claim as new.

01

Model × context configuration

A long-native-context model, a cheaper short-context model with a compact packet, and the same model with more history can yield different remaining-episode values. Hold task/scaffold fixed and separate model capability from packet length and content.

02

Preserve evidence, not just tokens

Compare raw history, structured evidence packets, retrieval, and structured handoffs. Measure omitted constraints and provenance, packet creation cost, and terminal outcomes—not only compression ratio.

03

Cache-aware switching

A switch discards the warm prefix cache; with cache reads at a fraction of base input price, the target must be much cheaper to pay back the re-read. Measure actual cache loss per switch and let it enter the continuation value rather than a fixed penalty.

04

Continuity boundaries

Tool loops and provider-held state make some checkpoints non-switchable. Restrict revisions to quiescent turn boundaries and measure how often a lock blocks a revision the policy would have taken.

05

Serving-aware constraints

Record actual input/output/cache tokens, queue time, and effective context limits. For self-hosted pools, benchmark KV memory and concurrency on the target stack rather than treating a simulation’s throughput assumptions as universal.

06

Reasoning budget as a lever

Keeping the model and raising or lowering its reasoning budget avoids a cache-breaking switch. Test a small effort menu only after Phases 1–2, and compare it with a model change at the same checkpoint.

Three different notions: a model’s native maximum context, the actual evidence packet supplied to it, and a serving pool’s configured/effective window. A larger allowed window is not automatically a larger API bill; actual token/cache usage and provider rules determine it. FleetOpt’s analytical pool results and Lost in the Middle motivate measurements, not guaranteed savings or universal claims about modern models.
